# Data sources

Every dataset the project uses, where it comes from, what has been verified about it,
and what it cannot tell us. All sources are free and public; none requires
registration, and nothing here involves circumventing an access control.

**Verification status.** Every source below has been pulled in full and hashed: 338
files, each with its URL, retrieval timestamp and SHA-256 in `data/raw/_manifest.json`,
retrieved on 20 September 2026 and re-verified byte for byte since (V2). The **Status**
row on each source records what was actually retrieved and over what window. Nothing is
described as verified that has not been seen.

## 1. Cboe VIX futures — per-contract settlement history

| | |
|---|---|
| **Provider** | Cboe Futures Exchange |
| **URL pattern** | `https://cdn.cboe.com/data/us/futures/market_statistics/historical_data/VX/VX_<settlement>.csv` |
| **Varying element** | `<settlement>` = the contract's final settlement date, `YYYY-MM-DD` |
| **Columns** | `Trade Date, Futures, Open, High, Low, Close, Settle, Change, Total Volume, EFP, Open Interest` |
| **Frequency** | Daily, one file per contract covering that contract's whole life |
| **Status** | **Retrieved** — 313 per-contract files, 2008-01-16 through the last listed expiry, all hashed in the manifest |
| **Used for** | Index reconstruction, term structure, open interest as the flow denominator |

**Why keyed by expiry rather than by trade date.** Requesting per contract means the
number of requests scales with the number of contracts (about twelve a year, roughly
230 for the sample) rather than with trading days, and the result arrives already
organised the way the index reconstruction needs it.

**How the file names are generated.** From the contract specification, not from a
directory listing: the final settlement date is the Wednesday 30 days before the third
Friday of the following month, moved to the preceding business day if that Wednesday or
the reference Friday is a holiday. Implemented and unit-tested in
`svcarry.index.calendar` against independently known expiries.

**Two archives, and why both are needed.** The modern per-expiry endpoint above does
not cover the whole history. It begins on 2013-01-02 and *truncates* every contract
already listed on that date — the January-2013 contract's modern file holds 10 rows
where its legacy counterpart holds 275. A legacy archive keyed by CME month code and
two-digit year,
`https://cdn.cboe.com/resources/futures/archive/volume-and-price/CFE_<code><yy>_VX.csv`,
covers the January-2008 through August-2014 expiries and is fetched as a companion
file (`VXL_<settlement>.csv`) wherever the modern endpoint served a boundary
contract. Dates are ISO in the modern files and US order (`MM/DD/YYYY`) in the legacy
ones, so each is parsed with an explicit format rather than by inference. Where both
archives price the same contract on the same day they agree in 13,126 of 13,127
cells; the single exception is adjudicated in `docs/validation.md` §V4.

**Known limitations.**
- Cboe writes `0.0000` for settlement on days a contract listed but did not trade. The
  pipeline sets non-positive prices to missing; treating a zero as a price would
  produce a −100% return in the index.
- **The modern archive also writes `0` for settlement across the whole of
  2013-01-02 to 2013-07-19 — 852 cells over 98 sessions — while populating every
  other column normally.** These are placeholders, not no-trade days. The legacy
  companion supplies a real price for 99.3% of them, and the loader prefers whichever
  row carries a settlement price before it prefers the modern archive. Getting this
  precedence the wrong way round leaves 95 consecutive sessions of 2013 unpriced;
  see `docs/validation.md` §V3b.
- **The settlement instant is not constant through the sample.** Cboe moved the VX
  daily settlement price calculation from 3:15 p.m. CT to 3:00 p.m. CT effective
  26 October 2020 ([notice](https://cdn.cboe.com/resources/release_notes/2020/Adjustment-of-Daily-Settlement-Time-for-Proprietary-Index-Products-Notice.pdf)),
  and replaced the calculation itself with a tiered VWAP/TWAP procedure effective
  9 September 2024 ([notice](https://cdn.cboe.com/resources/release_notes/2024/CFE-Updates-VX-and-VXM-Futures-Daily-Settlement-Process.pdf)).
  The first of these matters materially: 3:00 p.m. CT is 4:00 p.m. ET, which is when
  the exchange-traded products' consolidated closing price is struck, so index and
  product are measured together only from that date. Before it they are fifteen
  minutes apart, and the resulting asynchronicity is the dominant term in the
  pre-2020 tracking error (`docs/validation.md` §V6).
- Weekly VX contracts share the naming pattern. Only the monthly expiries generated by
  the calendar are requested, because the index is defined on the monthly cycle.
- Second-month liquidity is thin before roughly late 2005, which is part of the reason
  the sample starts in 2008.
- A handful of files contain rows dated after the contract's own settlement; these are
  dropped and counted.
- Fourteen legacy files prefix the CSV with a legal disclaimer line above the header;
  the parser locates the header row rather than assuming it is first.

**Redistribution.** Not redistributed in this repository. The acquisition script plus
the SHA-256 manifest reproduces the exact files.

## 2. Cboe index history

| | |
|---|---|
| **Provider** | Cboe |
| **URL pattern** | `https://cdn.cboe.com/api/global/us_indices/daily_prices/<NAME>_History.csv` |
| **Series used** | `VIX`, `VIX3M`, `VIX9D`, `VIX6M`, `VVIX`, `PUT`, `BXM` |
| **Layout** | `DATE, OPEN, HIGH, LOW, CLOSE`, or `DATE, <NAME>` for some strategy indices |
| **Status** | **Retrieved** through 2026-09-18: `VIX` from 1990-01-02, `VVIX` from 2006-03-06, `VIX6M` from 2008-01-02, `VIX3M` from 2009-09-18, `VIX9D` from 2011-01-04, `PUT` from 1991-03-04, `BXM` from 2002-03-22 |
| **Used for** | The implied leg of the variance risk premium; the term-structure signal; the PutWrite benchmark |

**The VIX3M constraint, and what is done about it.** The Cboe VIX3M file begins on
18 September 2009, which is inside the project's design window (2008–2015). The
`VIX/VIX3M` ratio therefore cannot be the primary term-structure signal without
truncating nearly two years of the design sample.

The project's response is to use the interpolated `cm30/cm90` ratio from the futures
curve as the **primary** slope measure — available for the whole sample, and arguably
the more appropriate measure since the strategy trades futures — and `VIX/VIX3M` as a
robustness variant, with an explicit test that the two agree on the period where both
exist. This is recorded as a methodological choice rather than presented as a free
lunch.

**PUT index coverage.** The Cboe file was observed to run from 1991; whether it extends
through the full sample end will be confirmed at pull time, and if it terminates early
the alpha regression's sample will be stated accordingly rather than quietly shortened.

**Redistribution.** Not redistributed; reproduced by the script.

## 3. Exchange-traded product and equity prices

| | |
|---|---|
| **Primary** | Yahoo Finance chart API, `https://query2.finance.yahoo.com/v8/finance/chart/<symbol>` |
| **Fallback** | Stooq, `https://stooq.com/q/d/l/?s=<symbol>.us&i=d` |
| **Symbols** | `VXX`, `VIXY`, `SVXY`, `UVXY`, `SVIX`, `SPY`, `^GSPC`, `^VIX` |
| **Status** | **Retrieved** (Yahoo) through 2026-09-18: `SPY` and `^GSPC` from 2004-01-02, `VIXY` from 2011-01-04, `SVXY` and `UVXY` from 2011-10-04, `VXX` (Series B) from 2018-01-25, `SVIX` from 2022-03-30 |
| **Used for** | Index tracking validation, the leverage-decay test, the VXX factor, and **SPY** OHLC for range-based realised variance (`^GSPC` is retrieved but not used for it: its opening print is stale, `docs/methodology.md` M7) |

**The split hazard, and why it gets its own paragraph.** VXX and UVXY have each been
reverse-split many times — a long-volatility product that decays 50–80% a year has to
be — and an unadjusted price series shows large fake positive returns on split dates.
Any comparison between a reconstructed index and a traded product is meaningless if
the adjustment is wrong.

The pipeline therefore keeps the raw close, the provider's adjusted close, and the
recorded split factors separately, and `docs/validation.md` reports an independent
reconstruction of the adjustment from raw close × cumulative split factor against the
provider's series. A discrepancy is treated as a finding, not a rounding difference.

**The VXX series break.** The original iPath VXX matured and Barclays launched the
Series B ETN in January 2018. The price history is two segments and must be handled
explicitly; a naive concatenation produces a spurious return on the changeover.

**Provider differences.** Yahoo returns raw OHLC plus an adjusted close and explicit
split events; Stooq returns series already adjusted. Which provider served each symbol
is recorded in the manifest, because the two are not interchangeable for the
adjustment check above.

**Redistribution.** Not redistributed.

## 4. Interest rates

| | |
|---|---|
| **Provider** | Federal Reserve Bank of St. Louis (FRED) |
| **URL** | `https://fred.stlouisfed.org/graph/fredgraph.csv?id=<SERIES>` |
| **Series** | `DTB3` (3-month bill, secondary market **discount rate**), `DGS3MO` (3-month constant maturity **yield**), `DFF` (effective fed funds) |
| **Status** | **Retrieved** — `DTB3`, `DGS3MO` and `DFF`, all three hashed in the manifest |
| **Used for** | The index total-return accrual and the strategy's collateral return |

**Discount rate, not yield.** The S&P VIX futures total-return indices and the
VelocityShares ETN "Daily Accrual" are both defined on the 91-day bill *discount* rate:

```
TBR_t = ( 1 / (1 − (91/360) · TBAR_{t−1}) )^(Δt/91) − 1
```

with `TBAR` the previous business day's discount rate as a decimal and `Δt` the
calendar days since the previous index business day. Using the constant-maturity yield
instead would give a subtly different accrual and break the comparison with the
products. `DTB3` is the discount-rate series and is what the pipeline uses; `DGS3MO` is
carried as a robustness alternative.

**Known limitations.** FRED writes `.` for non-observations (bank holidays that are not
exchange holidays). These become missing at load and are forward-filled for at most
five business days inside the accrual function, with the number filled recorded.

**Redistribution.** FRED series are in the public domain; small enough to commit if
useful, though the manifest makes it unnecessary.

## 5. SEC EDGAR filings

| | |
|---|---|
| **Provider** | U.S. Securities and Exchange Commission |
| **Documents** | See `config/filings.yaml` — seven filings across four issuers |
| **Status** | **Retrieved and read** — all seven archived in `references/filings/`, with **28 of 28** quoted terms re-found verbatim in the source documents by `scripts/extract_filing_terms.py` |
| **Used for** | Every product term the project asserts |

EDGAR's fair-access policy requires a descriptive User-Agent with a contact address and
asks for no more than ten requests a second. The HTTP layer supplies the header from
`config/config.yaml` and throttles well below that limit.

`config/filings.yaml` records, for each document, the **specific claims** it supports
and whether those claims have been read out of the archived file.
`scripts/extract_filing_terms.py` re-extracts every term from the archived document into
`reports/tables/filing_terms.csv`; any term that cannot be quoted from a primary
document is marked unverified there, with the results that depend on it flagged.

**The weakest input: assets outstanding.** Net assets by fund appear in the ProShares
10-K at period ends, not daily. Because the rebalancing-flow estimate is *linear* in
assets, the project constructs an upper and a lower bound between the disclosed anchors
rather than a point estimate, and requires its conclusion to hold at both. The method is
specified in `docs/methodology.md` M4 and its consequences are recorded in
`docs/limitations.md`.

**Redistribution.** SEC filings are public documents and are archived in
`references/filings/` so that a reader can check any quoted term.

## 6. Environment constraints affecting acquisition

Recorded here because they shaped the design rather than merely inconvenienced it.

The execution environment used to build this project reaches GitHub but is refused at
the egress proxy for `cdn.cboe.com`, `query2.finance.yahoo.com`,
`fred.stlouisfed.org`, `www.sec.gov` and PyPI. Two consequences are visible in the
repository:

1. **Every estimator is implemented in-repo** rather than imported from `statsmodels`
   or `arch`, and unit-tested against simulated data with known parameters. Where those
   packages are available the test suite cross-checks against them automatically and
   skips otherwise.
2. **The data was pulled from an unrestricted machine** by the same
   `scripts/fetch_data.py`, and every file was re-hashed against the manifest on
   arrival. That is where the manifest discipline comes from: it exists because the
   download and the analysis happen in different places and the join between them has
   to be checkable.

Nothing in this project substitutes a convenient source for a correct one because of
these constraints, and no result is reported from data that has not been downloaded.
